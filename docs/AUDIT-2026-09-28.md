## Findings requiring fixes

The save-mutation findings assume an operator has enabled writes and an authorized caller invokes an edit/restore. They are failures of the protection around authorized work, not claims of anonymous save-write access. Default read-only mode remains an important protection.

### A01 — P1: known vulnerable production dependency remains pinned

**Confirmed:** the main and PR lockfiles retain affected Next 16.2.12. See the preceding PR assessment for applicability and repair. This is a pre-existing baseline problem left unresolved by #16, not evidence that the grouped updates introduced the vulnerability.

**Acceptance:** implement the dependency plan above, with a real build-memory measurement and endpoint check. Do not retain the inaccurate “no `next/image`, therefore unexposed” rationale.

### A02 — P1: live REST proxy can bypass its endpoint policy and player redaction

**Confirmed, actual HTTP reproduction.** `src/app/api/palworld/[...path]/route.ts:114` validates only `path[0]`, accepts a second unvalidated segment, then joins both into the privileged game REST URL. Authorization and response filtering use the original first segment while URL normalization changes the requested resource.

The built app accepted **`GET /api/palworld/info/..%2Fplayers` without a session**, requested `/v1/api/players` upstream, and returned synthetic `playerId`, `userId` and `ip` fields. The response was handled as `info`, so player redaction and privacy were skipped. This is a confirmed disclosure boundary bypass; no game command was sent.

Signed-in requests also have no exact endpoint allowlist: `view.basic` allowed a synthetic `/settings` request using the game administrator credential. The contents of a real settings response were not obtained, so this report does not claim that passwords were leaked.

**Fix:** use a finite, exact method/path table mapped to upstream constants, required capabilities, guest policy and a response schema. Reject extra segments, decoded separators, traversal, unknown endpoints and unsupported methods before any fetch. Permit settings only through its intended settings capability and redacted backend route. Build the upstream URL from a constant selected by the validated route, not joined user input.

**Acceptance:** HTTP tests against the production build cover encoded slashes/backslashes, dot segments, case variants, extra segments, unknown paths and every role. Rejected inputs make zero upstream calls. Player responses cannot escape the player serializer through an alias.

### A03 — P1: guest disable and player privacy do not govern all live-player reads

**Confirmed.** The same proxy checks `guestMaySee(feature)` without enforcing the global guest setting/session capability. With `GUEST_VIEW_ENABLED=false`, `/api/auth/session` reported `guestAvailable: false` while anonymous `/api/palworld/players` still returned HTTP 200 and player names/locations.

`hiddenPlayerUids()` at line 27 returns an empty set when there is no token or the privacy service fails. Synthetic tests showed hidden players to a guest and to a signed-in caller during a privacy-service 503. The comment asserting that a missing backend means the live map has no data is false: the game REST service is independent, and the API response itself is a disclosure.

**Fix:** enforce global guest availability and the session's effective capabilities at the public boundary. Apply privacy to guests as well as users. Prefer a backend-owned live-player route that evaluates identity, visibility and redaction together; otherwise make the privacy lookup explicitly guest-capable and fail closed. Return a controlled unavailable result when visibility cannot be established. Use an explicit safe-field serializer for lower-privilege views.

**Acceptance:** global guest off, per-feature off, hidden player, guest, unlinked user, linked peer, staff, expired session and privacy outage combinations all have negative disclosure tests. Cover both save-derived and live REST paths.

### A04 — P1: guild marker tooltip renders player-controlled HTML

**Confirmed sink behavior and data flow.** `src/components/map-inner.tsx:960` passes `marker.guildName` directly to Leaflet `bindTooltip`, which treats string content as HTML. The neighboring popup escapes that same value. The guild-marker API copies the save-derived guild name (`backend/main.py:1779`) into the response.

A headless test using the installed Leaflet executed a synthetic image error handler when that tooltip opened. The entire in-game naming path was not exercised; a hostile name in imported or server save data reaches the unsafe sink. Viewers include the guild's members and staff, so this can execute with a more privileged dashboard session. HttpOnly cookies do not prevent script from making authenticated same-origin requests.

**Fix:** construct tooltip content with DOM `textContent`, and centralize the safe text helper for all dynamic Leaflet tooltips/popups. Audit neighboring string sinks rather than fixing only this occurrence. Add a compatible CSP as defense in depth, plus `frame-ancestors`, content-type and referrer protections where appropriate.

**Acceptance:** browser tests open tooltips with HTML-like guild/player names and assert literal text, no injected elements, and no script execution. Verify policy headers on the dashboard HTML as well as API responses. Do not break Leaflet positioning or Next's runtime with an untested blanket CSP.

### A05 — P1: the stopped-server proof accepts ambiguous failures and the wrong world

**Confirmed.** In `backend/safety.py:88–124`, REST `URLError` and TCP `OSError` classes are broadly classified as stopped. A synthetic DNS failure in both probes, an hour-old save, and an unknown process signal produced `editable: true`, `running: false`, `confidence: high`. This contradicts the stated fail-closed invariant: DNS failure says nothing about whether the game process is running.

Separately, `backend/savefiles.py:49` silently selects the newest world if configured `WORLD_GUID` is absent. A synthetic incorrect pin reproduced that fallback. A typo must not select a different mutation target.

**Fix:** distinguish refused connections from DNS, routing, timeout, permission and authentication uncertainty; uncertainty must prevent writes. Establish a trusted stopped-state/maintenance proof bound to the actual mounted world and game instance. For external servers without an authoritative signal, make the inability to prove stopped explicit rather than labeling stale files “high confidence.” Reject a missing configured world pin. Coordinate dashboard start/restart with the mutation lease in A06.

**Acceptance:** fault matrix for DNS, timeout, network failure, 401, mounted/unmounted/stale/wrong saves, missing pin and unavailable process information. Every ambiguous combination refuses mutation. Repeat the check immediately before committing files and test a server-start transition during a long edit.

### A06 — P1: concurrent edits/restores are not one serialized transaction

**Confirmed.** `backend/backup.py:525` checks safety and makes a backup but has no shared mutation lock. Two synthetic threads both entered `guarded_save_write` simultaneously. The backend has thread-pool handlers, and independent feature locks do not serialize all writers/restores/lifecycle commands.

That permits two plans based on the same save, lost updates, or one operation rolling back another operation's successful change. The two safety checks precede the body; lengthy parsing/re-encoding can also leave a long interval before the actual write.

**Fix:** introduce one per-world maintenance lease covering load/plan validation, backup, mutation, disk reread, rollback and invalidation. Include restore, settings changes where relevant, and dashboard-controlled start/restart. Account for multiple processes; an in-memory lock alone is not a durable interprocess contract. Make nested rollback/recovery calls safe without deadlocking. Recheck stopped proof and source identity at the commit boundary.

**Acceptance:** deterministic concurrent edit/edit, edit/restore, edit/start and failure/rollback tests show one operation owns the world, others receive a clear busy response, and no update disappears. Interrupted processes release/recover leases. Existing item-conservation and rollback tests still pass against the real fixture.

### A07 — P1: a pre-edit backup is not verified before the edit is allowed

**Confirmed.** `backend/backupstore.py:102` hashes source files, then separately calls `tar.add` on those paths. A file can change between those reads. The archive checksum covers the resulting archive but does not prove that each archived file matches the manifest. `create_backup` and `guarded_save_write` do not call the archive verifier before yielding.

A synthetic change between hash and archive insertion let the guard yield even though `verify_backup` subsequently returned `ok: false`, `Corrupted: Level.sav`. The code therefore does not deliver the documented “full verified backup before every mutation.”

**Fix:** archive a stable snapshot or hash the exact bytes inserted, validate source stability, then verify the completed archive and manifest before registering it as a usable rollback point or yielding the write guard. Mark/remove failed incomplete candidates without replacing a previous good backup. A07 must precede reliance on automatic rollback in A08.

**Acceptance:** mutate a source between collection/hash/read, simulate short reads and archive corruption, and require refusal before any live write. A valid verified archive still round-trips; recursive server backup folders remain excluded.

### A08 — P1: restore failure can leave partial live files without automatic recovery

**Confirmed.** `backend/backup.py:365` correctly verifies the source archive and takes a pre-restore backup. It then uses `shutil.copy2` into live targets with no automatic exception rollback or final readback validation. Injecting a copy error after a partial synthetic write left the destination containing `partial`.

**Fix:** preflight the entire selected manifest and target mapping; stage and validate files; commit with atomic replacement and durability handling; reread hashes; journal the multi-file operation; restore every already-touched target from the verified rollback point on error. Run under A06's lease. Resolve containment and reject symlink targets/replacements so local filesystem tampering cannot redirect recovery. Do not skip a selected missing source/config target and report an apparently complete restore.

**Acceptance:** corrupt archive rejection still occurs before writes. Fail each copy/replace/fsync/reread step, including the second of multiple files, and assert original bytes remain or automatic recovery is explicitly completed. Crash-recovery tests cover the journal. Preserve a manual recovery archive if automatic recovery itself fails.

### A09 — P1: self-export ownership survives account deletion and reuse

**Confirmed.** `backend/selfexport.py:69` keys exports by username, without an account-ID foreign key. `archive_for_download` at line 342 and `backend/main.py:4884` authorize by that username alone. A synthetic account was deleted and recreated with a new database ID and the same username; the replacement account could resolve the previous account's archive.

The download path also omits checks for the feature being disabled, expiry and whether the account is still linked to the archive's UID. Lazy retention runs on status/create, not directly on download.

**Fix:** bind archives to an immutable account ID and an explicit character/scope identity. Migrate or invalidate existing rows safely. Delete/revoke on account deletion, unlink/relink and relevant scope changes; recheck enabled state, ownership and expiry during download. Protect in-progress publication from account changes.

**Follow-up:** solo-guild eligibility and export parsing occur in separate world reads, and export copying can carry ancillary files. Add an archive-boundary check proving that every player file and retained guild belongs to the authorized snapshot. A cross-user export race was not reproduced; do not present that as a proven second disclosure.

**Acceptance:** deletion/recreation, rename if supported, unlink/relink, expiry, feature-disable and concurrent scope-change tests deny old downloads. Successful self exports contain only the allowed player's scoped data. Moderator full-world export retains its separate authorization.

### A10 — P1: repeated shutdown deadlocks lifecycle status

**Confirmed.** `backend/lifecycle.py:148` calls `status()` while holding a non-reentrant `_lock` when a watcher is already active. `status()` acquires the same lock. A synthetic repeated shutdown never returned and held the shared lifecycle lock, blocking later status/health/control calls that use it.

**Fix:** take a status snapshot without recursively acquiring the lock, or otherwise restructure the critical section. Make repeated shutdown requests idempotent and define how a new reason/timestamp affects an active watcher. Do not solve this by removing synchronization.

**Acceptance:** a second shutdown while watching returns promptly; status, health and subsequent control remain responsive; watcher completion leaves consistent state.

### A11 — P2: retention can delete recent safety backups

**Confirmed.** `backend/backup.py:481` applies `maxTotal` after adding grace-protected backups, replacing the keep set. With 51 fresh pre-edit backups and the default cap of 50, a dry run selected one for deletion despite the promised 48-hour grace.

**Fix:** separate protected/active rollback IDs from the discretionary retention budget. Never prune an archive held by a running transaction or its recovery journal. Report storage pressure and block new risky operations when necessary rather than silently violating the protection contract.

**Acceptance:** more protected backups than the cap, an active restore/edit, and mixed age buckets preserve all protected IDs. Dry-run and real pruning choose the same permitted deletions.

### A12 — P2: file cache keys miss same-size atomic replacements

**Confirmed.** `backend/savefiles.py:312` preserves old metadata with `copystat`; `backend/viewcache.py:64` keys on size and mtime only. Replacing synthetic `old` with same-sized `new` left the disk updated but the cached response equal to `old`. The forced Level parse after a guarded edit does not invalidate per-player `per_file` caches.

**Fix:** use a file identity/version stamp appropriate to replacement, such as device/inode plus size and nanosecond modification/change times, and/or explicit affected-file invalidation. Review the similar stamp used by `read_sav_bytes` for replacement races. Preserve intended permissions and account for save-activity safety when changing timestamp behavior.

**Acceptance:** same-size replacement with preserved mtime, player edit, restore, deletion/recreation and a replacement during a read cannot serve the old contents as current.

### A13 — P2: forced password rotation is advisory; lockout timing is misleading

**Confirmed.** `mustChangePassword` travels in account/session data but `backend/authz.py` still grants normal capabilities. A synthetic owner marked for rotation retained `users.manage`. Existing UI references label the condition without enforcing an initial rotation flow.

`backend/accounts.py:343` computes a delay from the count of failures but never expires a delay based on its start time. After a returned `Retry-After: 15`, the same account was still locked after 16 seconds; attempts remain inside a 15-minute window. This is a correctness/availability issue, not an authentication bypass.

**Fix:** allow only credential rotation/logout and minimal session metadata while rotation is required, enforced server-side and reflected in the UI. Give rate limiting an actual next-allowed deadline, or report the true remaining window. Honor forwarded IPs only through a configured trusted proxy chain. Separate password verification from opening a new session in the password-change route, and handle rate-limit errors there consistently.

**Acceptance:** temporary credentials cannot access normal protected routes; successful rotation revokes obsolete sessions; lockout expiry agrees with `Retry-After`; spoofed forwarding headers cannot manufacture independent IP budgets in the documented deployment.

### A14 — P2: exported CSV and settings text need semantic validation

**Confirmed primitive behavior.** `backend/reports.py:140` writes text beginning `=1+1` unchanged. Player-controlled guild/base names can reach CSV fields, so a spreadsheet may treat exported text as a formula. No spreadsheet was opened in this audit.

`backend/settings_ini.py:88` accepts newline-containing strings and non-finite floats such as `nan`; request changes are broadly typed. These can produce invalid settings. This is an authorized-settings correctness problem, not proof that an unprivileged user can edit settings.

**Fix:** encode potentially executable textual CSV cells safely for spreadsheet consumers, preserving real numeric columns; keep JSON exports unchanged. Validate INI values against supported key types/ranges, forbid CR/LF/NUL where invalid, reject non-finite numbers, handle quotes deliberately, and verify the written parse matches the requested values before reporting success.

**Acceptance:** CSV tests include `=`, `+`, `-`, `@`, tab/CR and ordinary names/numbers; INI tests include multiline strings, NaN/infinity, invalid enum/type/range, quotes and failed reread. Existing secret-redaction behavior remains intact.

### A15 — P1 for release gating / P2 for hardening: security checks do not block publication

**Confirmed repository configuration.** The active `protect-main` ruleset has only deletion and non-fast-forward protection; no required status checks or review rule. Legacy branch protection was absent. `.github/workflows/ci.yml` image publishing depends on backend/web, but the dependency audit is a separate workflow. A successful normal CI run can therefore coexist with a failed audit and proceed to publication after a main/tag push.

**Fix:** make the audit part of the release dependency graph (for example a reusable audit workflow plus an aggregate required check), run it on publish candidates, and configure the required checks on main. Ensure path filtering and skipped jobs cannot strand or bypass a required check. Review requirements should fit the maintainer workflow; automated check enforcement is the immediate need. Test tag releases as well as main.

The repository's default workflow token is already read-only and cannot approve PRs. Explicit top-level `permissions: contents: read`, tightly scoped publishing permissions and immutable action pins are useful hardening, not proof that current jobs have unrestricted write tokens.

**Acceptance:** a deliberately failing dependency audit blocks both merge eligibility and image publication; fork PRs receive no publish credential; normal and dependency-only PRs produce the same stable required-check names.

### A16 — P2: runtime and supply-chain inputs are not consistently tested or pinned

**Confirmed.** Docker builds/runs Node 20, while web CI uses Node 22. [Node 20 is EOL](https://nodejs.org/en/about/previous-releases). Python tests use 3.12 in CI, dependency audit/runtime target 3.11, and this local environment is 3.14.5. `PALSAV_REF=main`, mutable action tags and lower-bound-only Python requirements make builds resolve inputs independently.

A read-only audit of the **installed local environment** additionally reported 8 vulnerability records in 3 packages, representing 6 distinct CVEs: `httpx2 2.9.1`, `httpcore2 2.9.1`, and `pip 26.1.2`. HTTPX2 is a development/test dependency here, so this is not evidence that those libraries are exposed by the production web backend. The passing PR pip job audits runtime requirements and does not establish that the developer environment is current. `palooz` and `palsav-flex` were explicitly skipped because they are not on PyPI.

Plan a separate development-environment refresh: HTTPX2 at least 2.12.0, compatible httpcore2 at least 2.10.0, and pip at least 26.2.0, then rescan the resolved environment and rerun the affected tests. The advisories include [SOCKS WebSocket TLS handling](https://github.com/pydantic/httpx2/security/advisories/GHSA-7mj9-2mp8-4m2p), [response decompression amplification](https://github.com/pydantic/httpx2/security/advisories/GHSA-8xx6-hgc6-gc2m), and [pip's malicious-index URL handling](https://github.com/pypa/advisory-database/blob/main/vulns/pip/PYSEC-2026-3721.yaml). Their specific exploit prerequisites were not exercised. No local packages were upgraded during this audit.

**Fix:** align Node builder/runner and CI on a supported version; Node 22 is the smallest alignment step, with Node 24 a separately tested option. Preserve the matching Python 3.11 builder/runtime ABI until changing both deliberately. Add runtime-version CI coverage, lock Python dependencies, scan runtime and development graphs separately, pin the native parser to an immutable reviewed commit and submodules, generate an SBOM, and scan the final image/native libraries. Harden optional asset provisioning with bounded downloads/extraction and verified versioned digests where available.

Also tie local parser provenance to the container build: `setup-dev.sh` builds the archive in `refs/`, while Docker clones the upstream branch. Record and compare their source revisions so a local real-save pass can be associated with the parser actually shipped.

**Acceptance:** the same revision resolves reproducibly; tests cover the runtime Python; the installed image graph is scanned, not only the four direct requirements. Parser/Oodle round trips still pass on real fixture copies. Offline and missing-assets startup remains supported.

### A17 — P2: Docker build context omits important local-save exclusions

**Confirmed configuration gap, no publication leak demonstrated.** `.dockerignore` excludes `refs/`, `refworld/`, `.env`, caches and backups, but not the default `palworld/` bind-mount directory, arbitrary `*.sav` files or `PalWorldSettings.ini`. Dockerfile's `COPY . .` can send these to a local/remote builder and retain them in intermediate cache layers. Final standalone exclusions do not prevent that initial disclosure.

The audited build's standalone output did **not** contain the known private fixture/reference directories or save/config files. No such files are tracked in Git. Those checks do not establish that every operator's build context is safe.

**Fix:** explicitly exclude the supported live-data directories and save/config patterns from build contexts. Keep Git, Docker and standalone-output rules aligned through a synthetic sentinel test. Avoid relying on filename extension alone for databases or backups. Keep allowed public bundles/maps.

**Acceptance:** a synthetic default compose tree, secrets, player saves and world config never enter the build context or any exported image/cache layer; required public game-data bundles remain available.

### A18 — P2: request/resource limits and health reporting need strengthening

**Static findings.** Several Next proxy/auth fetches lack explicit deadlines. Long parsing work is called synchronously from some async handlers, and polling can overlap when requests are slow. Some upload size checks occur after buffering the body; the proxy may buffer it first. The public `/api/health` returns a shallow Next-only OK and does not establish backend readiness; the lifecycle deadlock is one example it can miss.

**Fix:** add bounded per-operation timeouts and cancellation, stream with byte limits before buffering at both boundaries, and run expensive work through a bounded worker/job mechanism coordinated with A06. Permit only one in-flight poll per resource, with cancellation/backoff and visible last-success state. Separate liveness from a bounded backend-aware readiness check. Keep LAN threat-model limits explicit rather than promising hostile multi-tenant availability.

**Acceptance:** slow/unreachable backend, client disconnect, oversized/chunked uploads, concurrent full-world jobs and a hung lifecycle do not create unbounded work or report ready. Normal offline/no-save startup continues to render clearly.

### A19 — P2: recovery scope and export disk usage are incomplete

**Static findings.** Moderator world-copy exports create unique unpacked directories and archives without a general retention budget. Self exports have narrower cleanup but the download expiry gap is in A09. World backups do not provide a documented recovery bundle for the separate SQLite accounts, sessions, audit and scheduler state.

**Fix:** add explicit export retention/quotas and safe orphan cleanup; reserve disk before large work. Provide an operator recovery procedure for dashboard state using SQLite's supported online backup mechanism and restricted storage, not a raw copy of a potentially active WAL database. Define session invalidation on recovery. Add a recovery drill spanning world data, settings and dashboard state.

**Acceptance:** repeated exports and interrupted jobs stay within a documented budget, active downloads/jobs are protected, disk-full refusal occurs before live changes, and a clean instance can restore the tested recovery bundle.

## Project changes, additions and removals to plan

### Requested addition: pruned dedicated-server export

**Recommendation: add this as a distinct export mode.** The requested outcome is a server-compatible copy of the world with selected players removed, preserving everyone else's original player UIDs. It should not convert anyone into the single-player host or require choosing a source/target UID.

This fills a real gap. `WorldExportRequest` currently requires `sourceUid` and `targetUid`; `soloexport.plan_export` rejects equal UIDs, and `exportscope` selects whole guilds. The existing moderator export can remap identities for another server as well as solo/co-op, but it cannot express “keep these players exactly as they are; remove these other players.” Self-serve solo export should remain its own workflow.

Proposed operator flow:

1. Open **Exports → Pruned server copy** and choose the source world/snapshot.
2. Select players to remove, grouped by guild. Optionally select a whole guild, but do not require whole-guild removal when only one member should go.
3. Preview retained/removed players, private Pals, inventories, containers, bases, guilds and other dependent records. Identify shared ownership and unsupported references explicitly. Show the retained-player list just as clearly as the removal list.
4. Resolve shared-asset decisions and replacement guild leaders, then approve the concrete preview. Bind the export to that snapshot and policy with a plan hash; reject stale plans.
5. Download a verified dedicated-server save bundle, with import instructions, game/schema version, file checksums and a summary of what was retained/removed. The live server and its saves remain untouched.

Proposed ownership rules, to be settled during implementation design:

| Data / case | Proposed behavior |
| --- | --- |
| Retained players | Preserve original UIDs and progression; no host conversion, rename or UID swap. Preserve player files byte-for-byte wherever no reference repair is required. |
| Selected player's private data | Remove the character, `.sav` and `_dps.sav`, private inventory/equipment/palbox and exclusively owned dependent records from the copy. Preview the actual scope before exporting. |
| Pals and items in shared guild/base use | Classify using the real ownership and reference graph. Do not assume an ownerless base worker belongs to the removed player, or delete a shared container because one reference disappears. Present explicit removal/transfer choices where ownership is shared. |
| Structures created by a removed member in a retained guild | Preserve shared bases by default, but explicitly repair/transfer applicable owner, builder and lock references to a selected retained member when supported. Refuse ambiguous cases instead of silently deleting the guild's base. |
| Removed guild leader, other members retained | Require a retained replacement leader and repair all membership/character-handle references. Never leave a leader pointing to a removed UID. |
| Guild with no retained members | Default proposal: remove the empty guild and its exclusively owned bases/workers/containers after reference analysis. Any transfer to a retained guild must be an explicit previewed option. |
| Files/fields of uncertain scope | Refuse publication if they could carry removed-player data or leave unresolved references. The current “copy unrecognized player files unchanged” behavior is unsuitable for a selective-sharing promise. |
| Settings, credentials and dashboard state | Omit server passwords, `.env`, dashboard SQLite/session/audit data, server rotating backups and unrelated exports. Offer a separately sanitized settings template only if useful. |

Implementation should use a **new server-export planner and verifier**, sharing proven serialization, archive and reference-walk primitives with the existing modules. Reusing whole-guild pruning is useful for the whole-guild case, but an arbitrary player removal needs an explicit graph of characters, guild membership, bases/map objects, item/character containers, work/expedition references and companion files. Check `docs/SAVE-FIELDS.md` and actual decoded data before declaring any ownership/reference location absent. Do not zero every matching GUID mechanically: some references must be removed, some reassigned, and some require refusal.

Build from one consistent snapshot into a fresh directory. A read-only copy can be assembled while the source server runs only if all relevant source files are captured consistently; retry/refuse a moving snapshot. Never operate on the live paths. Publish only after re-reading the serialized files, verifying referential integrity, confirming the selected players and their private data are absent from the supported scope, and proving retained identities remain unchanged. **A failed prune must produce no downloadable archive; never fall back to sharing the unpruned world.** The current moderator export's fallback is specifically inappropriate here.

Gate the feature with the existing full-world export/backup authority (`backup.manage`), or a narrower dedicated capability if desired; do not expose it through the ordinary player self-export permission. Bind download artifacts to immutable accounts as in A09, add expiry/quotas from A19, and audit the actor, snapshot, choices and outcome locally. Keep removed names/UIDs out of the recipient's manifest and bundled logs; internal audit detail can remain local. Describe this as selective player removal, not comprehensive anonymization of unknown historical/opaque fields.

Acceptance tests must cover removing one player from a multi-member guild, a leader with members remaining, a whole guild, private versus shared Pals/containers, orphan companion files, stale snapshots, partially decoded fields, serialization failures, and unchanged source-file hashes. Re-read the final archive independently and perform an isolated dedicated-server load/reconnect smoke test with retained players before claiming the format is ready to hand to another operator. Removing someone from a copy does not ban them from either server; banning is a separate action and is outside this feature.

**Delivery order:** implement after the snapshot/archive/export-ownership fixes (A07–A09) and storage controls (A19), with shared mutation-safety primitives reused where applicable. First extract a tested server-copy pipeline with no UID remapping; then add the per-player prune planner, explicit conflict decisions, strict archive verifier and UI. A guild-only first increment can reuse existing code, but it does **not** fulfill the requested specific-player workflow and must not be called complete on its own. Estimated size: L, chiefly because preserving shared assets and proving removal are harder than omitting player filenames.
