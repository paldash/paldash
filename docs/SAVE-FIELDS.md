# What is in a Palworld save, and what nothing here reads

`docs/savefields.json` is the exhaustive index, generated by
`scripts/mine-savefields.py`. This file is the curated front end, exactly as
`GAMEDATA-SOURCES.md` is to `datatables.json`.

**Read this before deciding a field is not in the save.** That is the whole
reason it exists.

---

## 1. Why

`mine-datatables.py` was built because the same mistake shipped twice: a feature
recorded that a table did not carry what it needed, a later feature *refused to
be built on those grounds*, and `DT_MapObjectAssignData` had the answer in 271
rows the whole time. Searching per-feature was the root cause.

**The save had the identical problem and no index.** Every field this project
reads was found while chasing one feature. In a single week that cost:

| What was missed | How it surfaced |
|---|---|
| `base_camp_level` on the guild record | A competing tool displayed it. The first check for it here sampled an `EPalGroupType::Organization` group instead of a `Guild` one and "confirmed" it was absent |
| `guild_markers`, `guild_chest_allowed_roles`, `role_permissions` | Three more on that same record, seen in the same glance |
| `WorkerDirector`, `GuildItemStorage` | Opaque blobs carrying container ids, found *after* this project documented per-base attribution as unavailable |
| 20 populated Pal fields (task #51) | One deliberate sweep — the proof the method works |

Generate the index with:

```bash
python3 scripts/mine-savefields.py \
    refworld/Level.sav \
    refs/palworld/.../Level.sav \
    refs/palworld/.../backup/world/<date>/Level.sav \
    --out docs/savefields.json
```

## 2. What the numbers mean

Three counts travel per path, because "set" means different things per field:

- **`seen`** — the key was present on this many entries.
- **`nonEmpty`** — not `None`, `""`, `[]` or `{}`.
- **`nonZero`** — additionally not `0`, `False`, the zero GUID, or an all-zero
  byte run.

**Presence is not occupancy.** A key on every Pal, populated on 0.1% of them, is
a different fact from one populated on all — which is why task #51's table is
non-default counts rather than key names.

`byVariant` buckets occupancy by the entry's own discriminator (`group_type`,
`concrete_model_type`, …). **This is the `base_camp_level` lesson**: a field
carried by one variant reads as "rare" when averaged across all of them, and as
"always present" when you happen to sample that variant first.

`readBy` is a **string-literal match** against `backend/*.py` and is approximate
in one direction only: it cannot prove a module reads that name *from this path*,
but a distinctive name appearing nowhere really is unread. Names in
`ambiguousNames` (`id`, `name`, `type`, `value`, `level`, …) collide with
everything and are excluded from the unread list rather than trusted.

**No values from a real world are in the committed index.** `refworld` holds real
Steam IDs, player names and guild names, so anything whose field name suggests a
person or place is reported as a count of distinct values and never printed.

## 3. The schema is bigger than any one world

**26 top-level `worldSaveData` structures across three saves, and no single save
has all of them.** refworld has 23.

| Structure | refworld | live | 07-22 backup |
|---|:--:|:--:|:--:|
| `BossSpawnerSaveData` | · | · | **X** |
| `CharacterParameterStorageSaveData` | X | X | · |
| `FixedWeaponDestroySaveData` | · | **X** | · |
| `LevelObjectRecoverPartySaveData` | · | **X** | · |
| the other 22 | X | X | X |

`BossSpawnerSaveData` existing **only in the oldest backup** is the one to note:
a single-world survey would have called it absent, and which world you happened
to pick would decide the answer.

Of the 111 paths that are not in every world, **82 are absent only from the
07-22 backup** — the smallest and earliest of the three (708k nodes against
2.4M). That is occupancy, not a schema difference: an early world has no oil
rigs and few dungeons, so the paths under them never appear. Fifteen more are
present only in the live world, for the same reason in the other direction.

This is why the script takes several saves. `verify-figures.py` already
establishes the reading: **a step change at one file is an artifact, a monotonic
trend across dated snapshots is drift.**

## 4. Where the unread fields are

260 paths carry a name no backend module mentions. By structure, with the
highest populated count in any world:

| Structure | unread paths | most populated |
|---|---:|---:|
| `MapObjectSaveData` | 77 | 9,052 |
| `CharacterSaveParameterMap` | 38 | 17,853 |
| `WorkSaveData` | 26 | 212 |
| `EnemyCampSaveData` | 15 | 423 |
| `FoliageGridSaveDataMap` | 12 | 4,573 |
| `DungeonSaveData` | 11 | 148 |
| `SupplySaveData` | 11 | 2 |
| `BaseCampSaveData` | 10 | 377 |
| `GroupSaveDataMap` | 9 | 16 |
| `DynamicItemSaveData` | 7 | 3,586 |
| `ItemContainerSaveData` | 7 | 194 |
| `GuildExtraSaveDataMap` | 6 | 840 |
| `MapObjectSpawnerInStageSaveData` | 4 | **27,591** |

Not all of it is worth reading — `FoliageGridSaveDataMap` is grass. The
interesting ones so far:

- **`MapObjectSpawnerInStageSaveData`** — 31,824 entries, entirely unread. The
  respawn state of the world's spawners.
- **`WorkSaveData`** — 160 entries with a `WorkAssignMap`. The dashboard infers
  base work from structures and Pals; this is the game's own record of it.
- **`EnemyCampSaveData`** — the state of the hunter camps the map draws.
- **`interact_restrict_type`**, **`concrete_model_type`**,
  **`stage_instance_id_belong_to`** — populated on nearly every map object.
- **`GotStatusPointList` / `GotExStatusPointList`** — 11,488 and 9,550
  populated, corroborating task #51's independent sweep.

## 5. Fixed-width opaque blobs — the prospects

A blob whose **width never varies** is the shape that has twice turned out to be
readable: `WorkerDirector` is 118 bytes with a container id at offset 98, and
`GuildItemStorage` is 20 bytes with one at offset 0. Both were documented as
unavailable first.

`byteLengthConstant` marks them. Ignoring `CustomVersionData` (engine metadata):

| Width | Count | Worlds | Path |
|---:|---:|:--:|---|
| 46 B | 6 | 3 | `BaseCampSaveData[].ModuleMap[].RawData` |
| 20 B | 1,616 | 3 | `MapObjectSaveData[].Model.RawData.unknown_bytes` |
| 12 B | 912 | 3 | `FoliageGridSaveDataMap[]…InstanceDataMap[].RawData` |
| 10 B | 43 | 3 | `MapObjectSaveData[].ConcreteModel.ModuleMap[].RawData.unknown_bytes` |
| 261 B | 4 | 2 | `DungeonSaveData[].MapObjectSaveData[].Model.RawData` |
| 7 B | 12 | 1 | `WorkSaveData[].WorkAssignMap[].RawData.unknown_bytes` |

**A constant width is a reason to look, never a reason to believe.** The rule
those two successes were won under is unchanged and non-negotiable:

> Reading a `ByteProperty` at a measured offset is only defensible with a
> verification attached. The decoded value **must resolve to a real entry in
> another structure**, or it is dropped — so a layout change yields *nothing*
> rather than a confident wrong answer.

`BaseCampSaveData[].ModuleMap[].RawData` at a constant 46 bytes on every base in
all three worlds is the strongest candidate here, and it sits beside
`WorkerDirector` in the same module map.

## 6. What this index does not tell you

- **What a field means.** It reports shape and occupancy. `base_camp_level`
  scales with base count, which makes "sum of the guild's base levels" the
  obvious reading and exactly the kind of inference this project refuses without
  evidence.
- **Whether a value is trustworthy.** refworld is a processed copy whose
  durability records were multiplied sixteenfold. Any figure taken from one save
  is a fact about that save until a second one agrees.
- **That an unread field is worth reading.** Most of `FoliageGridSaveDataMap` is
  grass. The list is a search space, not a backlog.
